## 二、根因分析

### 1. `llm.py:1312` `docs.aadd_texts()` 协程未 await（P0）

**文件**：`backend/app/services/llm.py::_paperqa_answer()`

```python
def _paperqa_answer(question, sources):          # 同步函数
    ...
    docs = Docs()
    for ev in sources:
        text = f"{ev.title}. {ev.snippet}".strip()
        ...
        docs.aadd_texts(text, doc=None)          # ← async 方法，未 await
        by_key[key] = ev
    answer = docs.query(question)
```

**根因**：paper-qa 的 `Docs.aadd_texts()` 是异步方法（`a` 前缀），在同步函数里调用且未 `await`，协程对象被丢弃、永不执行。

**影响**：
1. `Docs` 索引始终为空 → `docs.query()` 检索不到任何内容 → paper-qa 降级层名存实亡。
2. 每次触发打印 `RuntimeWarning: coroutine 'Docs.aadd_texts' was never awaited`（uvicorn 日志可见，紧随 `POST /api/chat` 之后）。

**修复**：`_paperqa_answer` 改为异步函数（`async def`），并 `await docs.aadd_texts(...)`；调用方（`answer_question` 的 paper-qa 分支）相应 `await`。若调用链不允许 async，则改用 `asyncio.run()` 包裹，或改用 paper-qa 的同步 API（若存在）。

### 2. `PUT /api/projects` 反复 422 + 结果未持久化（P1）

**文件**：`backend/app/api/projects.py::update_project` + `frontend/src/store/slices/projectSlice.ts` + `projectWorkspace.ts`

**现象**：
- uvicorn 日志中 `PUT /api/projects/46203615-...` 反复出现 `422 Unprocessable Entity`（与 `200 OK` 交错，呈间歇性）。
- 最新 workspace 里 `leaderboard`、`research.recommended`、`models`、`doe_plan`、`measured` 全部为空，但两次推荐任务（`e7cab0f8`、`870058c6`）均成功返回 3 条 recommended，且 6 条用 `Formulation` schema 校验全部通过。

**已排除**：推荐结果本身（`Formulation` 校验 OK）、最终保存的 workspace（校验 OK）。说明 422 是**异步操作中间态的瞬时非法数据**，且最终被「空」状态覆盖，导致结果丢失。

**根因（范围已锁定，待增强日志最终确认字段）**：
`buildWorkspacePayload()`（`projectWorkspace.ts`）对大部分对象字段做了 `sanitizeObjectArray`/`sanitizeObjectOrNull` 清洗，但以下字段**未做任何清洗/类型校验**，直接透传：

| 未清洗字段 | 后端 schema 约束 |
|-----------|-----------------|
| `selected_sources: list[str]` | 严格 `list[str]` |
| `source_types: list[str]` | 严格 `list[str]` |
| `active_constraints: list[str]` | 严格 `list[str]` |
| `optimization_history: list[float]` | 严格 `list[float]` |
| `rmse_history: list[dict[str, float]]` | 严格 |
| `measured: dict[str, float]` | 严格 `dict[str, float]` |
| `workbench_objectives_snapshot: list[dict]` | 严格 `list[dict]` |

推荐/DOE/台账三个异步操作完成后，前端把中间结果写回 store 并触发 autosave（防抖 `AUTOSAVE_MS`）。若某字段在中间态被塞入非标类型（如 `measured` 里出现字符串 `"-"`、`optimization_history` 里出现 `null`、`selected_sources` 里混入对象），Pydantic 立即拒绝整包 → 422 → 保存失败 → 结果随下一次成功保存（空状态）被覆盖丢失。

**修复（三管齐下）**：
1. **增强日志（定位）**：`update_project` 端点加 `try/except ValidationError`，记录 `e.errors()` 的 `loc/type/msg` 到 logger —— 下次复现即可精确定位到具体字段。
2. **前端加固**：`buildWorkspacePayload` 对上述未清洗字段补类型过滤（字符串数组滤掉非 string、数字数组滤掉非 number、`measured` 滤掉非数值），与现有 `sanitizeObjectArray` 同风格。
3. **后端宽容（可选）**：`ProjectWorkspace` 对易漂移字段放宽为 `list[Any]`/`dict[str, Any]` 并加 `model_validator` 归一化，或对 422 场景降级为「忽略非法字段仅告警」而非整包拒绝。

### 3. `NH3·H2O` 水合物「·」分隔符不支持（P2）

**文件**：`backend/app/domain/chemistry.py::molar_mass()` / `_parse_mass()`

**现象**：celery 日志 `recommend_meta` 中出现 `'氨水: Unparseable formula segment in \'NH3·H2O\' at 3'`。

**根因**：`_parse_mass` 的 `_TOKEN` 正则 `([A-Z][a-z]?)(\d*)|(\()|(\))(\d*)` 不匹配水合物分隔符 `·`。`molar_mass("NH3·H2O")` 走 chemformula（AssertionError）→ 回退 `_parse_mass` → 在 `·` 处 `match.start() != pos` → 抛 `ValueError`。氨水等含水/结晶水的配方成分无法计算摩尔质量。

**修复**：`_parse_mass` 支持 `·` 分隔符 —— 按 `·` 拆分（`NH3·H2O` → `NH3` + `H2O`），各段独立计算后求和；或预处理把 `·` 归一为 `+`/`.` 再解析。水合物语义上等于加合（NH3·H2O = NH3 + H2O）。

### 4. qLogEHVI C++ 扩展编译失败（P3，非阻塞）

**现象**：`UserWarning: Failed to compile fused qLogEHVI C++ extension: Ninja is required... Falling back to pure-Python (~3x slower)`。

**根因**：botorch 首次 qLogEHVI 需 JIT 编译 C++ kernel，缺少 `g++`/`ninja`。

**修复**：`.venv` 内补装 `ninja`（`g++` 已装），首次编译成功后缓存于 `~/.cache/torch_extensions/`。纯正确性无关，仅性能回退。
